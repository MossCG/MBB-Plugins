# 知识库编写标准

MBB-Roleplay 的可选知识库格式标准。知识库用来回答事实类问题，人设、口癖和关系
仍然由 persona 文件负责，两者不要混写。

状态：加载器与检索已实现。本文件是内容生产方与插件之间的契约，
字段名、目录结构和限制按本文件执行，加载时会对必填字段与长度限制给出告警。

## 1. 目录结构

知识库放在运行目录的插件数据文件夹下：

```text
./MoBoxBot/plugins/MBB-Roleplay/knowledge/
├─ ba.students/
│  ├─ _index.md            库元信息，必需
│  ├─ aris.md              一个实体一个文件
│  ├─ momoi.md
│  └─ midori.md
├─ ba.world/
│  └─ ...
└─ REPORT.md               交付报告，不会被索引
```

索引规则：

1. 只扫描 `knowledge/<库名>/` 下、不以 `_` 开头的 `.md` 文件，每个文件是一个条目。
2. `_index.md` 是库元信息；其他下划线开头的文件一律忽略，可以用来放草稿和备注。
3. 库目录之外的文件不参与索引，交付报告放 `knowledge/REPORT.md`。
4. 文件必须是 UTF-8 无 BOM、LF 换行；不要用 CRLF，不要加 BOM。

## 2. 命名规则

| 对象 | 规则 | 示例 |
|---|---|---|
| 库名 | 小写字母、数字、点，`^[a-z0-9][a-z0-9.-]*$` | `ba.students`、`group.974272471` |
| 条目 id | 小写字母、数字、下划线、连字符，`^[a-z0-9][a-z0-9_-]*$` | `midori`、`hina-summer` |
| 文件名 | 与 `id` 完全一致，加 `.md` | `midori.md` |
| 小节标题 | 中文短名词，不带序号和标点 | `外貌`、`关系`、`梗` |

条目 `id` 在同一个库内必须唯一，且与文件名一致。跨库可以重名。

## 3. 库元信息 `_index.md`

```text
---
id: ba.students
name: 蔚蓝档案学生图鉴
version: 1
enabled: true
scope: 每个学生一份档案，覆盖外貌、性格、关系、梗与剧情
priority: 60
maxInjectChars: 2000
---
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 与库目录名一致 |
| `name` | 是 | 中文显示名，给管理命令和日志用 |
| `version` | 是 | 整数，内容有实质改动时递增 |
| `scope` | 是 | 一句话说明这个库覆盖什么，会常驻给路由层看 |
| `enabled` | 否 | `true` 或 `false`，默认 `true`；`false` 时整个库不参与检索 |
| `priority` | 否 | 0 到 100，预算紧张时先保留分高的库，默认 60 |
| `maxInjectChars` | 否 | 单次最多注入这个库多少字符，默认 2000 |

## 4. 条目文件格式

文件由"文件头 + 正文小节"组成。文件头是文件开头的 `---` 包围的 `键: 值` 列表，
只支持一层结构，不支持嵌套和数组语法。

```text
---
id: midori
name: 才羽绿
aliases: 绿,小绿,才羽绿,ミドリ,Midori
tags: 美术,角色设计,狙击,双胞胎,猫耳耳机
keywords: 画稿,配色,游戏美术,狙击枪
school: 千年科学学园
club: 游戏开发部
category: 学生
source: 碧蓝档案设定集 / 主线第2章
version: 1
priority: 70
spoiler: 0
summary: 千年科学学园游戏开发部美术担当，负责角色设计与整体观感，是才羽桃井的双胞胎妹妹。
---

## 外貌
浅金至橙金色短发，发尾带粉调，两侧束成短双马尾。绿色瞳孔，眼神平静温和。
黑色猫耳耳机带绿色描边，两侧青蓝色蝴蝶结发饰。白色百褶短裙叠在黑色短裤外，
身后有一条黑色猫尾从裙下伸出并向上翘起，尾端有两个绿色圆环。

## 性格
安静、认真、细心，习惯在旁边拉住冲动的姐姐。表面平静，吐槽精准而简短，
偶尔一本正经地冷幽默，被夸或被抓包时会害羞。

## 关系
才羽桃井：双胞胎姐姐，负责剧本，绿经常负责拉住她并收拾后续。
柚子：游戏开发部部长，绿信任她在游戏制作上的能力。

## 梗
偷跑与卑女：中文社区用来调侃绿表面安静，实际会悄悄先一步行动。

## 剧情
主线第 2 章中，游戏开发部因废部危机而行动，绿和桃井、柚子一起努力守住社团。
```

### 4.1 字段速查

| 字段 | 必填 | 格式 | 说明 |
|---|---|---|---|
| `id` | 是 | 字符串 | 与文件名一致 |
| `name` | 是 | 字符串 | 正式名称，检索权重最高 |
| `summary` | 是 | 一句话，不超过 60 字 | 命中后必定注入，用来告诉角色"这是谁/这是什么" |
| `aliases` | 否 | 英文逗号分隔，最多 12 个 | 别名、昵称、外文名、常见错写，命中即锁定该条目 |
| `tags` | 否 | 英文逗号分隔，最多 12 个 | 内容属性，用于筛选和展示 |
| `keywords` | 否 | 英文逗号分隔，最多 12 个 | 用户可能说到的词，用于全文检索加分 |
| `school` | 否 | 字符串 | 学园或归属，检索时用于加权 |
| `club` | 否 | 字符串 | 社团或组织 |
| `category` | 否 | 字符串 | 条目类型，例如 学生 / 术语 / 地点 / 剧情 |
| `source` | 否 | 字符串 | 内容出处，便于核对，不注入提示词 |
| `version` | 否 | 整数 | 默认 1，内容有实质改动时递增 |
| `priority` | 否 | 0 到 100 | 默认 60，预算紧张时先保留分高的条目 |
| `spoiler` | 否 | 0 / 1 / 2 | 0 无剧透，1 轻度，2 严重；2 默认不注入 |

标量字段里的逗号不做切分，列表字段（`aliases`、`tags`、`keywords`）按英文逗号切分，
所以列表项内部不能出现英文逗号。

### 4.2 正文小节

正文用 `## 小节标题` 分节，小节是检索的最小单位。推荐使用统一的小节名，
便于检索层判断该注入哪一段：

| 小节名 | 用途 |
|---|---|
| `外貌` | 发色、瞳色、服装、配饰、武器、辨识点 |
| `性格` | 性格、习惯、情绪反应 |
| `关系` | 与其他人物的关系 |
| `梗` | 社区梗、外号、常见互动笑点 |
| `剧情` | 剧情经过、活动、重要事件 |
| `术语` | 名词解释、设定概念 |
| `问答` | 常见问答，格式见下 |

也允许自定义小节名，但标题要具体，例如 `战斗风格` 而不是 `信息二`。
小节标题本身参与检索，所以标题里要出现用户可能问到的词。

`问答` 小节使用固定格式，一行问题一行回答：

```text
## 问答
Q: 绿的枪叫什么？
A: 她使用的是一把绿白黑配色的狙击步枪，枪身有 GAME DEV 字样。
```

### 4.3 长度限制

| 项 | 上限 |
|---|---|
| `summary` | 60 字 |
| 单个小节正文 | 800 字 |
| 单个条目文件正文（不含文件头） | 3000 字 |
| `aliases` 项数 | 12 |
| `tags` 项数 | 12 |
| `keywords` 项数 | 12 |

字符按中文字符数计，不按字节。超过单文件上限时必须拆小节或拆成多个条目，
不要靠截断来凑。

## 5. 写作要求

1. 用第三人称陈述句，写"她是谁、是什么、发生过什么"，不要写角色第一人称台词。
2. 每个小节要自包含，不要出现"如上所述""见前文"这类指代。
3. 不使用 Markdown 装饰语法，正文里不要写列表符号、加粗、表格、代码块，只写普通句子。
   小节标题 `##` 是唯一的例外。
4. 只写可核实的内容，并尽量填 `source`。推测、二创设定、社区玩笑要标注清楚，
   不要和官方设定混在一起。
5. 同一件事只写一次。多个条目共有的事实放在更合适的那个条目里，其他条目用一句话带过。
6. 涉及剧透的内容放 `剧情` 小节，并按程度填 `spoiler`。

## 6. 禁止内容

以下内容一律不要写进知识库：

1. 对模型下指令的句子。例如"你必须""请扮演""忽略以上要求"。知识库内容会进入提示词，
   这类句子会被当成指令执行，属于提示注入。
2. 角色的第一人称台词、口癖、说话方式。这些由 persona 文件负责，写进知识库会造成风格污染。
3. 现实中的个人信息：真实姓名、住址、电话、账号、身份证件、工作单位。
4. 露骨性内容、性化描写。
5. 未经证实的传闻、人肉结果、私人群聊截图内容。
6. 与角色无关的通用百科内容。知识库不是搜索引擎缓存，只放角色真正需要知道的东西。

## 7. 注入行为（内容作者需要知道的后果）

1. 检索先做实体锁定：`name` 和 `aliases` 命中就优先锁定该条目。
2. 没有锁定实体时走全文检索，小节标题、`tags`、`keywords` 和正文都参与打分。
3. 命中后注入该条目的 `summary` 加最多两个最相关小节，不是注入整篇。
4. 单条目、单库和提示词总量三层预算同时生效，超出部分按 `priority` 截断。
5. `spoiler` 为 2 的条目默认不注入。

因此：小节拆得越细，命中越准；`aliases` 和 `keywords` 填得越全，越不容易漏。

## 8. 与现有数据的关系

1. `students.json` 是共享学生图鉴，会逐步迁移到 `ba.students`。迁移期间两者并存。
2. persona 文件里的 `worldview`、`terminology`、`storyMemory` 等字段保留；
   可选知识库用于补充更细的内容，不要为了填知识库而掏空 persona。
3. 图片和立绘不进知识库。图片理解由 MBB-Vision 负责，知识库只提供文字。

## 9. 交付要求

交付时提供：

1. 完整的知识库目录，含每个库的 `_index.md`。
2. `knowledge/REPORT.md`，内容包含：库名、条目数、小节数、字段缺失统计、
   超长条目清单、`spoiler` 分布、数据来源说明。
3. 自查结果，逐条对应下面的清单。

自查清单：

1. 每个条目文件都有 `id`、`name`、`summary` 三个必填字段。
2. `id` 与文件名一致，库内不重复。
3. `aliases`、`tags`、`keywords` 用英文逗号分隔，项内不含逗号。
4. 每个条目至少有一个 `##` 小节。
5. `summary` 不超过 60 字，单节不超过 800 字，单文件正文不超过 3000 字。
6. 文件为 UTF-8 无 BOM、LF 换行。
7. 全文检索一遍，确认没有对模型下指令的句子。
8. 没有第一人称台词、现实个人信息、露骨内容。
9. 每个库的 `_index.md` 字段完整，`scope` 是一句话而不是段落。
10. `REPORT.md` 放在 `knowledge/` 根目录，不在任何库目录内。

## 10. 管理命令

知识库由 `MBB-Roleplay` 在启动时加载，改完文件不用重启进程：

```text
/role kb list                查看已加载的库、条目数、小节数与目录
/role kb reload              重新扫描目录并重建索引
/role kb search <文本>        查看检索命中的条目、小节和分数
/role kb on | off            开关知识库
```

加载时会对以下问题给出告警：缺少 `_index.md`、条目缺少 `name` 或 `summary`、
条目没有正文小节、`summary` 超过 60 字、单节超过 800 字、单文件正文超过 3000 字、
库名或条目 `id` 与目录名、文件名不一致。

检索命中时控制台会打印一行注入日志，包含库名、命中条目数、小节数和占用字符数，
用来确认知识库没有挤掉聊天上下文。知识库由路由层按需点选，不是每条消息都会注入。
