## 为什么它的缓存命中率看起来更高

### 1. 稳定系统提示词和动态上下文分层明确

MaiBot 的 Planner 和 Replyer 都把主要人设、行为规则和输出格式放在固定 system 内容中。
时间、目标消息、回复参考、临时风格和本轮额外要求放在后面的 user/context item 中。
当前时间通常追加在请求尾部，而不是塞在系统提示词中段。

对应实现：

- `src/maisaka/chat_loop_service.py`
- `src/chat/replyer/maisaka_generator_base.py`
- `prompts/zh-CN/maisaka_chat.prompt`
- `prompts/zh-CN/maisaka_replyer.prompt`

MBB-Roleplay 可以学习的是：

- 固定 persona、规则、工具能力和输出格式继续放在最前。
- 时间、关系、情绪、召回资料和当前消息全部放在稳定块之后。
- 秒级时间不再进入系统动态块，直接进入当前 user 消息。

### 2. 历史是追加式结构化上下文

MaiBot 的 Planner 维护结构化的消息 item、工具调用和工具结果，并通过上下文压缩处理长会话。
它尽量保持消息身份、引用、`session_id` 和 `msg_id` 稳定，避免每轮重新拼接一份完全不同的自然语言摘要。

对应实现：

- `src/maisaka/context/messages.py`
- `src/maisaka/context/history.py`
- `src/maisaka/context/compaction.py`

MBB-Roleplay 不需要立刻重写上下文协议，但应继续保持：

- 当前群使用稳定 `sessionId`。
- 工具结果作为当前回合内的结构化消息追加。
- 工具 schema 在一轮内固定，不因 `tool_search` 反复改变请求前缀。
- 长期记忆仍按相关性注入，但不要把秒级、分钟级字段插到稳定块中。

### 3. 它专门统计“理论前缀命中”和“API 实际命中”的差值

MaiBot 的 `llm_cache_stats.py` 会按任务、请求类型、模型和会话记录：

- 服务端返回的命中 Token 与未命中 Token。
- 本地对最近 128 份完整请求计算的理论公共前缀。
- API 命中率与理论命中率的差值。
- 第一处动态差异路径。
- 是否疑似发生上下文滑窗，头部丢了几条消息。
- 低命中调用点和高命中调用点。
- 每次进程重新启动后的运行批次对比。

这部分比单纯展示总缓存率更有价值。总缓存率会被路由、复核、记忆整理等短请求稀释，
也可能被一次超长最终回复拉高，无法直接说明提示词前缀是否组织合理。

MBB-Roleplay 可借鉴的下一步：

- 在现有 `RoleplayAiLog` 和 `/ai usage` 上增加调用层标签。
- 为回复、路由、复核、私聊、随机刻分别统计缓存率。
- 对回复层记录稳定前缀字符数、首次请求命中率和工具循环后续命中率。

## 为什么它更像活人聊天

### 1. Planner 和 Replyer 分工清晰

Planner 只判断何时说、对谁说、要不要查资料或调用工具，并给出回复方向。
Replyer 不在大段规则里继续做决策，只根据目标消息、最近历史和表达风格写一句自然回复。

MBB-Roleplay 已经采用路由层和执行层分工，应继续坚持：

- 判断是否回复、引用谁、是否使用技能的规则留在路由层。
- 执行层只关注当前消息、必要背景和具体表达。
- 不再把大量工具说明、通用禁令和角色剧情重复塞进执行层。

### 2. 回复器提示词短，表达风格单独维护

MaiBot 的 Replyer 模板本身很短，主要只包含：

- 名字和人格。
- 日常、口语化回复要求。
- 可编辑的表达风格。
- 群聊注意事项。
- 只输出正文的后处理要求。

它把表达方式、备用风格、群聊黑话、表情包和错别字等拆成独立配置或后处理模块。

MBB-Roleplay 当前稳定规则偏长，后续应逐步把可编辑内容从 Java 字符串迁出：

- 通用聊天规则保留。
- 角色表达、口癖和具体场景规则放回 persona。
- 低频词、网址过滤、动作解析等能本地处理的约束少写进模型提示词。

### 3. 主动制造“不完美”

MaiBot 提供可配置的注意力漂移、短反应、错别字、分段发送、打字速度和表达候选。
这些功能不是为了降低质量，而是让句子长度、开头、停顿和情绪代价变得不均匀。

可以学习的部分：

- 短反应和长回复混合，但低频。
- 分段发送按语义切，不机械按固定字数切。
- 偶尔的省略、改口、半句和无语反应。
- 对同一角色保留多个可轮换的表达候选。

暂不照搬的部分：

- 默认中文错别字。角色型机器人需要稳定识别人名、术语和承诺，错字应由人设明确允许时再开启。
- 过碎的短消息。小桃、小绿这类角色不应长期只回一两个词。
- 多个差异很大的临时风格。角色扮演需要稳定人格，临时风格只适合低频使用。

### 4. 消息身份和引用关系结构化

MaiBot 的每条上下文消息都带 `msg_id`、会话、时间、用户、群名片、引用目标和自己的消息标记。
这让模型更容易区分“谁在说”“回复的是哪一句”“哪条是自己说的”。

MBB-Roleplay 已有 QQ、引用和 `[自己]` 标记，应继续避免：

- 只靠昵称识别人。
- 把引用内容拼成普通正文。
- 把另一机器人的消息混成自己的历史。

## 对 MBB-Roleplay 的具体调整建议

### 应立即改

- 当前时间从 system 动态块移到 user 消息。
- 一轮工具循环固定 `tools` schema。
- 复核和风格这类无状态小请求使用稳定的角色级或任务级会话。
- 本地 Qwen 风格层暂时退出主链路，避免一次效果不稳定的额外模型调用。

### 应逐步删

- “法律、道德、合规”式助手边界话术。
- 重复的“不要说教、不要冷冰冰拒绝、不要客服腔”同义规则，保留一条总原则即可。
- 已在本地清洗器处理的角色名前缀、括号动作和 Markdown 禁令。
- 与当前角色无关的固定职业梗和项目词。

### 应保留

- QQ 身份、引用、自己和他人消息的结构化区分。
- 反提示词注入、外部内容信任边界、现实隐私和后端权限限制。
- 路由层与执行层分离。
- 回复复核、重复检测、链接过滤、工作区与工具调用。

### 可继续学习

- 按调用点统计实际缓存率与理论缓存率。
- 结构化历史与上下文压缩。
- 可轮换表达候选和低频短反应。
- 语义断句，而不是只按字符上限硬切。
- 拟人节奏、打字状态和发送节拍联动。
