# 群内只用一种播报版式，图片只走主程序 renderText 并一律回退文本

状态：accepted（2026-10-22）

跑团插件发给群里的消息承担三种用途：KP 会照着念、玩家会截图转发、新手靠它判断下一步做什么。原型（消息流原型）比较过三种群内版式：[A 播报风](../prototype/one-session-message-flow.md)（`【标题】`）、B 沉浸风（`▍标题` + 装饰线）、C 极简风（`[标签]` 一行一项），并把 B/C 留给呈现规范真机比较。比较结果是 v1 只做 A，理由不是审美：B 的装饰线在 QQ 窄消息体与不同字号下会折行成两截，C 的方括号与 A 的 `【】` 混排让同一类信息在两种符号间跳，而三种版式并存意味着同一条场景叙述在不同配置的群里长得不一样，可复制性丢失。标题词表因此冻结成一张表（【开团】【检定】【AI 叙述】等 24 个），新增标题要先改表再改代码。图片同样收窄：主程序 API 只暴露 `ImageUtil.renderText(String title, List<String> lines)`（760px）与 `ImageUtil.toBase64Uri(byte[])`，仓库里虽然有两处直接用 AWT 自绘的图片（`MBB-Status/StatusImageRenderer`、`MBB-Roleplay/RoleplayMemoryImageRenderer`），但那是主程序内部白名单下的先例，插件引入 AWT 会让「只依赖 `org.moboxlab.moboxbot.API`」的边界失效，也无从保证运行环境有可用字体。因此本插件所有图片只用 `renderText`，版式靠行约定表达（标题行、元信息行、`【节名】` 独立成行、每行 ≤26 全角字符），并且渲染失败一律回退纯文本——回退文本在规范里冻结成固定字段，不临时拼。图片保留在三处：进场景的情景卡、结束时的战报、剧本打印页；角色卡与检定结果不发图，因为它们要能被复制和引用。

## 考虑过的选项

- **保留三种版式由配置切换**：配置位留了（`presentation.style`），但只实现 `broadcast`；三套实现意味着三套模板、三套字数预算与三套验收样例，而收益只是换皮，不采用。
- **用 AWT 自绘战报图（照抄 `StatusImageRenderer`）**：视觉可控、能做真正的卡片排版；代价是违反插件只依赖 API 的边界、依赖运行环境字体、并且与主程序升级节奏耦合，不可行。
- **图片失败时抛错或中止流程**：会让「图片失败不影响继续游戏」这条判据直接不成立；改成回退文本后游戏流程与图片完全解耦。
- **按模板类型分别决定群内单条上限**：上限碎片化后，拆分器要记住十几种阈值；统一成 500 字 + 每类消息一个「内容上限」（§3 表）两级预算，拆分逻辑只有一套。
- **私聊也拆多条**：私聊拆条更容易丢条与乱序（尤其角色卡与 KP 提示需要整体阅读），改为不拆、超长折叠。

## 后果

- 消息文案全部收口到 `docs/MBB-Trpg-presentation.md`；指令集 里「文案归 呈现规范」的 8 处、AI 主持 的 5 条接口级要求、数据模型与存档 的战报排版归属，都指向这一份文件。规格装配 装配 `docs/MBB-Trpg.md` 时直接引用，不复制。
- 实现被拆成五个纯函数类 + 一个出口类（`TrpgMessageTemplates` / `TrpgMessageFormatter` / `TrpgMessageSplitter` / `TrpgImageTemplates` / `TrpgPresenter` + `TrpgPresentConfig`），前四个可脱离 QQ 与 AWT 单测，出口类用 `FakeSender` 测；这是本插件第一个可单测的层，也因此把「构建脚本要能跑测试」作为 实现切片 的前置显式登记。
- 已知限制：行宽 26 字是按 760px 与默认字号估算的，真机若裁字只调 `wrapForImage` 的常量；`presentation.style` 是个只接受一个值的配置位，将来要加版式得同时改模板、词表与验收样例。
- 安全边界：线索全文、KP 提示、NPC `secret` 这类私密信息私聊失败时只发提示、绝不回退到群内；回退只适用于无秘密的公开消息（情景卡、战报、脚本打印页）。
